# IT ACADEMY — інструкція запуску (v3: посилений захист даних)

## Що в архіві
| Файл | Призначення |
|---|---|
| `index.html` | увесь фронтенд (три інтерфейси: Student, Moderator, NAVI Admin) |
| `schema.sql` | таблиці, RLS, захищені RPC, серверні події, журнал, Realtime. Ідемпотентний для повторного запуску на цій схемі |

**Edge Functions не потрібні для цієї версії.** Усі чутливі операції (призначення модераторів, блокування, розблокування, пульс) зроблені як `SECURITY DEFINER` RPC у `schema.sql`: вони самі перевіряють роль того, хто викликає (`auth.uid()`). `service_role` ключ ніде не використовується і не повинен потрапляти у frontend.

## Запуск
1. **Supabase → SQL Editor** → вставте весь `schema.sql` → Run.
2. **Project Settings → API**: скопіюйте `Project URL` і `anon / publishable` ключ у початок скрипта `index.html` (`SUPABASE_URL`, `SUPABASE_ANON_KEY`). Секретний ключ не копіювати.
3. **Authentication → URL Configuration**: у `Site URL` вкажіть адресу сайту на Cloudflare Pages, а в `Redirect URLs` додайте її ж (інакше посилання відновлення пароля не повернуть на сайт).
4. **Authentication → Providers → Email**: залиште Email увімкненим. Якщо вимкнете «Confirm email», реєстрація одразу входить в акаунт; якщо ввімкнете — користувач спершу підтверджує пошту.
5. Зареєструйтесь на сайті, потім у SQL Editor виконайте:
   `update profiles set role='admin' where email='ВАШ@EMAIL';`
   (єдиний спосіб зробити адміна; з сайту роль `admin` призначити не можна).
6. **Database → Replication / Realtime**: таблиці `events, announcements, profiles, messages, audit_log` додаються в публікацію `supabase_realtime` самим `schema.sql`. Якщо Realtime вимкнено для проєкту — увімкніть.
7. Cloudflare Pages: якщо проєкт підключений до GitHub — зробіть commit і push оновлених файлів у підключену гілку; Cloudflare автоматично виконає деплой. Якщо проєкт створений через Direct Upload — завантажте оновлений `index.html` вручну (збірка не потрібна).

## Ролі й правила
| Дія | user | moderator | admin |
|---|---|---|---|
| Власні оцінки/предмети/цілі | ✔ | ✔ | ✔ |
| Бачити інших користувачів і рейтинг | ✘ | список звичайних користувачів (без оцінок) | ✔ усе, рейтинг лише тут |
| Блокувати / розблокувати звичайного користувача | ✘ | ✔ (причина + термін) | ✔ |
| Блокувати модератора або адміністратора | ✘ | ✘ | ✔ (себе — ні) |
| Призначати / знімати модераторів | ✘ | ✘ | ✔ |
| Змінювати власну роль | ✘ | ✘ | ✘ |
| Журнал дій, історія блокувань, Live Activity | ✘ | лише власні дії | ✔ |

Блокування: причина (3–300 символів), виконавець, дата, термін (1 год / 1 день / 7 / 30 днів / безстроково). Тимчасові завершуються автоматично: статус рахується за часом на сервері, а при наступному пульсі (кожні 45 с) база закриває запис. Заблокований користувач: втрачає доступ до всіх даних (RLS), його сесія завершується через Realtime або пульс, вхід показує причину й термін.

## Додатковий захист у v3
- `last_seen`, роль, блокування, email та системні дати не можна змінювати з браузера; `last_seen` оновлює лише `heartbeat()`.
- Тригер БД перевіряє, що предмет належить тому самому користувачу, що й оцінка; додатковий складений зовнішній ключ додається, якщо в наявних даних немає порушень.
- Події реєстрації, оцінок, цілей і зміни профілю записуються тригерами бази даних. Клієнт не має права вставляти або редагувати `events`. Події входу не записуються, бо клієнтський сигнал не є надійним підтвердженням.
- Адмінські вибірки користувачів, оцінок, предметів, цілей і блокувань завантажуються сторінками по 1000 рядків. Інші стрічки мають окремі обмеження відображення.

## Перевірка після запуску (виконайте самі)
1. Дві вкладки: адмін і звичайний акаунт. Адмін → «Користувачі» → «Призначити модератором»: у другому акаунті панель змінюється без перезавантаження.
2. Модератор блокує користувача на 1 годину з причиною: користувач миттєво вилітає, а на вході бачить причину. «Розблокувати» повертає доступ.
3. Модератор не бачить кнопок для адмінів і модераторів. Перевірка на сервері: у консолі браузера (під модератором)
   `await sb.rpc('ban_user',{target:'<id адміна>',why:'тест'})` → помилка «Модератор може блокувати лише звичайних користувачів».
4. Захист профілю: спроба змінити `last_seen` з браузера має завершитися помилкою.
5. Захист ролей: у консолі звичайного користувача
   `await sb.from('profiles').update({role:'admin'}).eq('id',S.u.id)` → помилка тригера. Так само `blocked:false` для себе.
6. Адмін → «Журнал»: усі дії записані; спроба `delete` або `update` на `audit_log` відхиляється.

## Відомі обмеження
- Рейтинг і аналітика рахуються в браузері адміністратора з усіх завантажених даних; для дуже великих баз доцільно перенести агрегати на сервер.
- Адміністратор може заблокувати іншого адміністратора (так вимагає ТЗ), але не себе. Модератор може зняти блокування, поставлене адміном, якщо цільовий користувач звичайний.
